## R1. 解析（CSV 和 ANZ 对账单）

**输入**：CSV 文件文本（R1A、R1B），或 ANZ 对账单读出来的文字行（R1C）+ 账户的银行
**输出**：`ParsedRow[]`，每行 `{ date: 'YYYY-MM-DD', amountCents: number, description: string, balanceCents: number | null, rowIndex: number }`

按 `financial_account.bank` 选解析器：

| bank                  | 解析器 | 说明                               |
| --------------------- | ------ | ---------------------------------- |
| anz                   | R1A    | CSV。PDF 对账单用 R1C（2026-10-28） |
| cba                   | R1B    |                                    |
| anz_plus、cash、other | 无     | 不能导入 CSV，只能手动录入（R8.1） |

### R1.0 两个解析器共用的规则

> R1A、R1B 两个 CSV 解析器都用。R1C 对账单只用第 4（金额）、6（出错整份失败）、7（按文件顺序输出）条。

> 引用下面某一条时写 `R1.0-N`，如 `R1.0-4` 是金额。

1. 用 Papa Parse 解析，兼容带引号和不带引号的列
2. 跳过空行和只有空白的行；支持 CRLF 和 LF
3. 日期 `DD/MM/YYYY` → `YYYY-MM-DD`，非法日期报错
4. 金额**按字符串转成分**，不用 `parseFloat` 再乘 100（会有浮点误差）。允许前面带 `+` 或 `-`
   - `"-58.40"` → `-5840`
   - `"+500.00"` → `50000`
   - `"2000.00"` → `200000`
   - `"0.72"` → `72`
   - `"5"` → `500`
   - 金额为 0 报错
5. 描述：去掉首尾空白，**保留中间原样**（清洗在 R3 做）
6. 任意一行出错 → 整个文件解析失败，错误信息带行号，**不导入任何一行**
7. 输出顺序和文件一致（两家银行都是新的在前），不在解析层排序

### R1A ANZ

- 没有表头，3 列：日期、金额、描述
- 金额带引号，描述不带引号
- 描述不带引号，里面有逗号时会被切成 4 列以上：第 3 列以后用 `,` 拼回去当描述。少于 3 列报错
- `balanceCents` 为 `null`

| 输入行                                                                                | 输出                                                                                                                                |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `29/09/2026,"-58.40",VISA DEBIT PURCHASE CARD 1111 COLES 0559 MELBOURNE`              | `{ date: '2026-09-29', amountCents: -5840, description: 'VISA DEBIT PURCHASE CARD 1111 COLES 0559 MELBOURNE', balanceCents: null }` |
| `02/09/2026,"2000.00",ANZ M-BANKING FUNDS TFER TRANSFER 815033  FROM       400006691` | `{ date: '2026-09-02', amountCents: 200000, ... }`                                                                                  |
| `31/02/2026,"-1.00",X`                                                                | 报错：第 n 行日期非法                                                                                                               |
| 空行                                                                                  | 跳过                                                                                                                                |

### R1C ANZ PDF 对账单（2026-10-28 新增，M6.6）

ANZ 账户除了 CSV，还能导入 PDF 对账单。对账单的账期是固定的、首尾相接，每行都有余额，所以用来**补漏和自动对账**：平时照样导 CSV（及时），对账单出来后把 PDF 导进同一个账户，CSV 已有的被 R4 跳过，漏掉的补上，期初期末自动填进 R9。

2026-10-28 用一份真实的 Access Advantage 半年对账单（50 笔）和同账期的 CSV 对过：日期、金额、描述（多行拼起来）**全部一致**，余额逐行连续，最后等于汇总页的期末余额。所以同一个账户 CSV 和 PDF 可以混着导，不会重复。

2026-10-29 换成 `unpdf` 读，又试了 Joint、Progress Saver 各一份：格式有 5 处和最初写的不一样（汇总、账号、`OPENING BALANCE`、换年少一个 `blank`、合计行前面的 `blank`），下面已经改过来。改完以后三份都解析成功、三项检查通过，Access Advantage 50 笔还是和 CSV 全部一致。

**两层**：

1. 读文字（`src/server/pdf/`，用 `unpdf`）：把每一页的文字按坐标拼成行，同一行里隔得远的两段之间放两个空格，返回 `{ page, text }[]`。读不出文字（扫描件）→ 报错"读不出文字"
2. 解析（`src/lib/import/anz-statement.ts`，纯函数）：输入上面的行，输出和 R1 一样的 `ParsedRow[]`，外加账期、期初期末、账号尾号。测试只用 `fixtures/anz-statement/` 里编的文字，不用 PDF

**表头**（找不到任何一项 → 整份失败）：

- 有一行含 `ANZ` 和 `STATEMENT`
- 账期：`DD MONTH YYYY TO DD MONTH YYYY`（如 `04 MARCH 2026 TO 04 SEPTEMBER 2026`）→ `periodFrom`、`periodTo`
- **账期是 `(periodFrom, periodTo]`**（2026-10-28 定）：`OPENING BALANCE` 那行的日期是 `periodFrom`，是那天结束时的余额，`periodFrom` 当天的交易在上一份对账单里。上一份的 `periodTo` = 这一份的 `periodFrom`
- 账号：`Account Number` 后面的 `dddd-ddddd`，可能在同一行，也可能在后面 3 行里（汇总页左右两栏拼在一起，号码常常在下面几行）。去掉 `-` 后要以账户的 `number_suffix` 结尾，不然整份失败"这份对账单不是这个账户的"。账户没填尾号也失败，提示先去账户设置填。**账号不存、不进日志，错误信息里最多带后 4 位**
- **自动认账户**（2026-10-29 加，M6.6-6b）：导入对账单不用先选账户。用账号去找本家庭**没归档的 ANZ 账户**里 `number_suffix` 和账号尾部对得上的：
  - 正好一个 → 导入这个账户，之后照上一条核对
  - 一个都没有 → 整份失败"找不到尾号是 dddd 的 ANZ 账户，先去账户设置填上尾号"（dddd 是账号后 4 位）
  - 两个以上（尾号填得太短）→ 整份失败"有 n 个 ANZ 账户的尾号都对得上，去账户设置把尾号填长一点"
  - 找不到账号 → 整份失败"找不到账号"
  - CSV 里没有账号，还是要选账户
- 汇总：`Opening Balance`、`Closing Balance`、`Total Deposits`、`Total Withdrawals`。标签后面可能带冒号，也不一定在行首（左栏的姓名、BSB 会拼在同一行前面）。金额取标签之后、同一行或后面 4 行里的**第一个金额**（`$` 常常单独一行，中间可能隔着左栏的文字）。取错了会被下面的三项检查拦下

**交易行**：

- 以 `DD MON`（如 `05 MAR`）开头，最后三段依次是支出、存入、余额。支出和存入**恰好一个是金额、另一个是 `blank`**，余额是金额
- 栏位的位置每页不一样，**不按列宽切**，按"最后三段"认
- 例外：换年时，只有年份的那行会占掉下一笔的一个 `blank`（PDF 里 `blank` 印在交易行上方，读文字时和年份拼成一行），这一笔末尾只剩**金额、余额两段**（倒数第三段不是金额也不是 `blank`）。这时用上一笔的余额（第一笔用期初）判断方向：上一笔余额 − 金额 = 这一行的余额 → 支出；上一笔余额 + 金额 = 这一行的余额 → 存入；都不是 → 整份失败
- 金额：去掉千分位逗号，按 R1.0-4 转成分。支出是负数，存入是正数
- 描述：交易行里日期之后、金额之前的部分，加上后面的续行，用一个空格拼起来，去首尾空白。和 CSV 的描述一致（R4 的 `normalizedDescription` 会合并空白，空格多少不影响去重）
- 续行：下一行既不是交易行，也不是下面要跳过的行，就是描述的续行
- `OPENING BALANCE` 那行不是交易，**最后一段**是余额，要等于汇总页的期初。真实对账单里这行是 `DD MON  OPENING BALANCE  余额`，它的 `blank  blank` 跑到了上面年份那行
- `balanceCents`：解析出来给检查用，**不写进 key、不存库**（R4.1：ANZ 的 key 不放余额，不然和 CSV 对不上）

**跳过的行**：`EFFECTIVE DATE ...`（实际消费日期，不拼进描述）、`TOTALS AT END OF PAGE`、`TOTALS AT END OF PERIOD`（前面可能多一个 `blank`；PERIOD 那行最后还有期末余额）、页眉页脚（`Page n of m`、对账单标题、`Account Number`、`Transaction Details`、栏位标题 `Date  Transaction Details ...`）、只有年份和 `blank` 的那行（`blank` 可能是一个或两个）。汇总页、对账单最后的说明页没有交易行，不影响

**年份**：交易行只有日和月。

- 按出现顺序（旧的在前），起始年份 = `periodFrom` 的年份；月份比上一笔小（如 DEC → JAN）就加一年
- 遇到只有年份的那行（`2026  blank  blank`），以它为准
- 算出来的日期不在 `(periodFrom, periodTo]` 里 → 整份失败
- 正好等于 `periodFrom` 时，错误信息单独写"账期第一天有交易，R1C 对账期的假设不对"，要回来改规则（这个假设是从 `OPENING BALANCE` 的日期推的，还没见过首日有交易的对账单）

**检查**（任何一条不过 → 整份失败，什么都不导，错误带第几笔和页码）：

- 期初 + 逐笔金额 = 每一行的余额（读错了一行就会在这里断开）
- 最后的余额 = 汇总页的期末
- 支出合计、存入合计 = 汇总页的 Total Withdrawals、Total Deposits

和 CBA 不一样：CBA 的余额不连续只警告（R1B.1），对账单是银行给的正本，对不上多半是解析读错了，所以拒绝。

**输出顺序**：和文件一致（旧的在前，和 CSV 相反）。R4.1 的 `occurrence` 只对完全相同的行计数，顺序不影响结果。

**一笔都没有**（这个月没有交易）：照样能导入，只建 `import_batch` 做对账和首尾衔接（R12.2）。

**R9 的日期范围**：`import_batch.date_from` 存 `periodFrom` 的第二天，`date_to` 存 `periodTo`，R9 照旧按 `[date_from, date_to]` 算，正好是 `(periodFrom, periodTo]`。

### R1B CBA（2026-10 用真实导出确认）

- 没有表头，4 列：日期、金额、描述、余额，**全部带引号**
- 金额和余额都带正负号：`"+500.00"`、`"-20.00"`、`"+12345.67"`
- 同一天里也是新的在前

| 输入行                                                                      | 输出                                                                                                                       |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `21/10/2026,"+500.00","Transfer from xx5678 CommBank app Home","+12345.67"` | `{ date: '2026-10-21', amountCents: 50000, description: 'Transfer from xx5678 CommBank app Home', balanceCents: 1234567 }` |

### R1B.1 余额连续性检查

对相邻两行（文件顺序，第 i 行比第 i+1 行新）：

```
balance[i] − amount[i] == balance[i+1]
```

- 不成立 → **不报错**，导入照常进行，导入结果里显示警告"第 i 行和第 i+1 行之间余额不连续"
- 这能发现文件被手动改过、或银行导出不完整

### R1B.2 自动得出期初期末余额

- 期末 = 第一行（最新）的余额
- 期初 = 最后一行（最旧）的余额 − 最后一行的金额
- 自动填进 `import_batch` 的 `opening_balance_cents`、`closing_balance_cents`，然后跑 R9，不用手动填

## R2. 提取和脱敏

在清洗之前做。顺序：**先提取，再脱敏**。

### R2.1 提取卡号后四位

- 正则：`/\bCARD (?:XX)?(\d{4})\b/i`
- ANZ：`VISA DEBIT PURCHASE CARD 1111 COLES 0559 MELBOURNE` → `1111`
- CBA：`Myer Pty Ltd Docklands VI AUS Card xx1234 Value Date: 17/09/2026` → `1234`
- 没有匹配 → `null`

### R2.2 提取转账对方账号

- 只在描述含 `FUNDS TFER` 或 `TRANSFER` 时提取（不区分大小写）
- 两种格式：
  - 完整账号（ANZ）：`/\b(?:FROM|TO)\s+(?:\d{6}-)?(\d{8,})\b/i`。账号前面可能带 6 位 BSB 和 `-`（转去 ANZ Plus 是这种，2026-10-25 用真实导出确认），BSB 不算账号
  - 银行已经打码的尾号（CBA）：`/\b(?:FROM|TO)\s+XX(\d{4})\b/i`
- `TRANSFER 681801  TO  012345400006691` → `012345400006691`
- `TRANSFER 815033  FROM       400006691` → `400006691`
- `TRANSFER TO 012345-400000004 #123456` → `400000004`（带 BSB；`#123456` 是参考号，不提取）
- `TRANSFER FROM 012345-400000004 #123456` → `400000004`（转入方向还没见过真实导出，先按同样格式处理）
- `Transfer from xx5678 CommBank app Home` → `5678`
- `Transfer To MISS X Y PayID Phone from CommBank App Eat Eat` → `null`（PayID 转账只有人名，没有账号）
- 注意 `681801`、`815033` 是转账流水号，不是账号，不提取
- 提取出的数字**只在内存里用于 R6 匹配，不入库**

### R2.3 脱敏

- 把描述里所有**连续 8 位及以上的数字**替换成 `****` + 后 4 位
- `TO  012345400006691` → `TO  ****6691`
- `FROM       400006691` → `FROM       ****6691`
- `EASI AU 280672605`（9 位）→ `EASI AU ****2605`（宁可多脱敏）
- `TRANSFER TO 012345-400000004 #123456` → `TRANSFER TO 012345-****0004 #123456`（6 位 BSB 和参考号不受影响）
- CBA 的 BPAY 客户号、贷款号、直接扣款参考号也会被脱敏：`LN REPAY 700006979` → `LN REPAY ****6979`
- BPAY 账单码 `{022288}`（6 位）、门店号 `0559`、卡号后四位、流水号 `681801`（6 位）、CBA 的 `xx5678` **不受影响**

## R3. 清洗商家名

**输入**：脱敏后的描述
**输出**：`merchant`（大写字符串）

ANZ 和 CBA 用同一套步骤，不适用的步骤自然不生效。按顺序执行：

1. 转大写
2. 去掉 ANZ 交易类型前缀（只去开头）：
   - `VISA DEBIT PURCHASE CARD \d{4}`
   - `ANZ INTERNET BANKING BPAY` → 替换成 `BPAY`
   - `ANZ M-BANKING FUNDS TFER` → 替换成 `TRANSFER`，并去掉后面的 `TRANSFER \d+`
   - `EFTPOS`
   - `NON-ANZ ATM` → 替换成 `ATM`
3. 去掉 CBA 的附加信息：
   - ` VALUE DATE: \d{2}/\d{2}/\d{4}`
   - ` AUS CARD XX\d{4}`
   - CBA 的 BPAY：`^(.+?) COMMBANK APP BPAY .*$` → `BPAY $1`（和 ANZ 的格式统一）
   - 转账里的 ` TO PAYID PHONE`、` PAYID PHONE`、` FROM COMMBANK APP`、` COMMBANK APP`
4. 去掉开头的支付通道前缀：`ZLR*`、`SQ *`、`SMP*`、`LS `、`\d+PIN* `（如 `794PIN*`）
5. 去掉 BPAY 账单码：`\{\d+\}`
6. 反斜杠 `\` 替换成空格
7. 连续空白合并成一个空格，去掉首尾空白
8. 反复去掉结尾的地区词：`AU`、`AUS`、`VI`、`VIC`、`VICAU`、`NS`、`NSW`（至少保留一个词）

## R4. 去重

### R4.1 生成 key

```
dedupe_key = sha256( account_id | date | amount_cents | normalizedDescription | occurrence | balance_cents )
```

- `balance_cents`：CBA 有余额，写进 key；ANZ 没有，写空字符串。ANZ 的 PDF 对账单虽然有余额，也写空字符串（R1C），不然和 CSV 的 key 对不上
- `normalizedDescription`：**脱敏后**的原始描述，转大写，连续空白合并为一个空格，去首尾空白（不是 merchant，清洗规则以后会改，key 不能跟着变）
- `occurrence`：同一个文件内，`(date, amount_cents, normalizedDescription)` 完全相同的第几笔，从 1 开始，按文件里的出现顺序计数

### R4.2 导入时

- 数据库里已有相同 `(account_id, dedupe_key)` → 跳过，计入 `duplicate_count`
- 没有 → 继续走 R8（pending 匹配）和插入

| 场景                                                   | 结果                              |
| ------------------------------------------------------ | --------------------------------- |
| 文件里同一天同店两笔 `-4.50`                           | occurrence 1 和 2，两笔都插入     |
| 同一个文件导入两次                                     | 第二次全部跳过                    |
| 9 月 1 到 30 日已导入，再导 9 月 15 日到 10 月 15 日   | 9 月 15 到 30 日跳过，10 月的插入 |
| 先导的文件里某天有 2 笔相同，后导的文件里同一天有 3 笔 | 前 2 笔跳过，第 3 笔插入          |

## R5. 归属人

归属人的含义是**钱用在谁身上**，不是谁付的钱。卡号只能说明谁付的，所以优先级排在分类后面。

| 4      | 账户的 `default_member_id`                                          | account       |

系统分类和 Uncategorised 没有分类默认，直接走 3、4。

## R6. 内部转账识别

### R6.1 自动识别（导入时）

条件全部满足：

- 描述含 `FUNDS TFER` 或 `TRANSFER`
- R2.2 提取出了对方账号数字
- 这个数字和本家庭某个 `financial_account.number_suffix` **尾部对得上**，且不是当前账户自己
  - 提取的数字以尾号结尾（ANZ 完整账号的情况），或
  - 尾号以提取的数字结尾（CBA 只给 4 位的情况）

结果：`transfer_status = auto`，分类设为系统分类"内部转账"，`category_source = system`

- 对上**多个**家庭账户（如提取到 `5678`，家里有 `115678` 和 `225678`）→ 不认成转账，走 R7，留给 R6.3 兜底
- 没有尾号的账户（现金）不参与匹配

| 对方账号          | 家庭账户尾号    | 结果                       |
| ----------------- | --------------- | -------------------------- |
| `012345400006691` | 某账户 `6691`   | auto                       |
| `400006691`       | 某账户 `6691`   | auto                       |
| `400006691`       | 某账户 `006691` | auto（尾号 4 到 6 位都行） |
| `400006747`       | 没有匹配        | 不是内部转账，走 R7        |
| `5678`（CBA）     | 某账户 `5678`   | auto                       |
| `5678`（CBA）     | 某账户 `115678` | auto                       |
| `5678`（CBA）     | 某账户 `0567`   | 不匹配                     |

**PayID 转账没有账号**（如 `Fast Transfer From <人名>`），R6.1 认不出来，靠 R6.2 配对或 R6.3 兜底。

### R6.2 配对

每次导入完成后，对**整个家庭**里还没配对的 `auto` 转账（包括以前导入的），在对方账户里找另一半：

- 对方账户 = R6.1 匹配到的那个账户
- 金额相反（`a = -b`）
- 日期相差 ≤ 2 天
- 对方那笔还没配对

找到恰好 1 笔 → 两边互相写 `transfer_pair_id`。另一半如果还不是转账（比如 CBA 那边只显示人名，被分成了 Uncategorised）：

- `transfer_status` 改成 `auto`，分类改成内部转账，`category_source = system`
- 如果另一半的分类是 `manual`，不改它，只配对，并在 F8 提示（R16.7）。`transfer_status` 也不改（保持 `none`），因为 auto 不计收支，改了等于把手动分类从统计里抹掉

找到 0 笔（对方账户还没导入）或多笔 → 不配对，不影响它被标成转账。

为什么要对整个家庭重跑：先导 ANZ joint、后导 CBA 时，转账的识别发生在 ANZ 那边，要等 CBA 导进来才找得到另一半。

### R6.3 兜底建议

导入完成后，对**本次导入新插入的**交易里，**不是**转账、且属于"未分类"的：

- 在本家庭其他账户里找：金额相反、日期相差 ≤ 2 天、也是未分类、还没配对（候选可以是以前导入的）
- 恰好 1 个候选 → 两边都标 `transfer_status = suggested`，配对
  - "恰好 1 个"要求**两边互相**都只有对方这一个候选。A 只有 B，但 B 有 A 和 C 两个候选 → 不建议
- 只从本次新插入的交易出发，是为了每一对只在后导入的那一边进来时检查一次。拒绝过的两笔都是旧交易，以后的导入不会再建议（撤销后重新导入会再建议一次，可以接受）
- 为什么只建议不自动生效：朋友 AA 的转账（PayID，R6.1 认不出）可能刚好和另一笔金额相反、日期接近，要人来判断

确认前**按普通交易统计**（还是未分类）。在 F8 里确认或拒绝，两边一起改：

| 字段             | 确认                                  | 拒绝       |
| ---------------- | ------------------------------------- | ---------- |
| transfer_status  | `confirmed`                           | `none`     |
| 分类             | 内部转账                              | 保持未分类 |
| category_source  | `manual`（人决定的，R7.2 不会覆盖）   | 不变       |
| transfer_pair_id | 保留                                  | 清空       |
| 归属人           | 不变（未分类和内部转账都没有分类默认，R5.1 重算结果一样） | 不变       |

- 从任意一边发起都行，两边一起改，一个事务。不是 `suggested`、两笔没有互相配对时报错，什么都不改
- 有多个拆分的交易不能确认（内部转账不该有别的分类的拆分），提示先删掉拆分；拒绝不受影响（2026-10-24 补）

### R6.4 账户尾号改变后重新识别（2026-10-25）

R6.1 只在导入时跑。账户是后来才建的、尾号是后来才填的、或者规则后来才补上的（比如 ANZ Plus 带 BSB 的格式），以前导入的转账就一直是普通交易。所以**保存带尾号的账户时**（新建或编辑，尾号变没变都算），对本家庭的旧交易重跑一次：

1. 候选：本家庭其他账户里 `transfer_status = none`、没有 `transfer_pair_id` 的交易
2. 对候选的**脱敏后**描述跑 R2.2 和 R6.1，只看能不能对上**这个账户**。脱敏后完整账号只剩 `****1234`，按 R12.1 的方式当 4 位尾号匹配（这个账户的尾号以这 4 位结尾）；同时对上家里多个账户的照 R6.1 不算
3. 对上的按主拆分来源处理：

| 交易 | 处理 |
| --- | --- |
| 只有主拆分，`category_source = rule`，或未分类 | `transfer_status = auto`，分类改成内部转账，`category_source = system`，归属人按 R5.1 |
| 分类是 `manual` | 不改，计数 |
| 有多个拆分 | 不改，计数 |
| `suggested`（R6.3） | 不在候选里（第 1 步已排除），留给用户在 F8 确认或拒绝 |

4. 改完对整个家庭跑一次 R6.2 配对（这个账户能导入时，另一半可能已经在了）

保存前弹窗："有 N 笔旧交易会认成内部转账（另有 M 笔分类是手动的或拆分过，不改）。要改吗？"。N 是 0 就不弹，直接保存。选"不改"也照样保存账户，只是不动交易。一个事务。

- 改尾号时，以前按**旧尾号**认成转账的交易不退回去。很少见，真遇到了在 F8 手动处理
- 尾号是空的不触发
- 已经认过的交易 `transfer_status` 不是 `none` 了，不在候选里，所以重复保存不会重复改，N 一般是 0、不弹

例子 2（带 BSB）：ANZ Male 里有一笔 `TRANSFER TO 012345-****0004 #123456`（规则补上以前导入的，是 Uncategorised）。编辑 ANZ Plus Male（尾号 `0004`）直接保存 → 弹窗 N = 1 → 变成 auto、Internal transfer。

例子 1：建 fixtures 家庭时 CBA Female 先不填尾号，导入 `joint-2026-09.csv`：#11 `TRANSFER TO ****0003` 认不出，是 Uncategorised、Home（account），和 #18 一样。给 CBA Female 填上 `0003` 保存 → 弹窗 N = 1 → #11 变成 auto、Internal transfer、Home（account）。再导入 `cba/female-2026-09.csv`，#11 和 CBA #10 照常配对。

## R7. 分类

对每笔新交易，按顺序，**第一个命中的生效**：

1. 已经被 R6.1 标为内部转账 → 内部转账
2. 系统规则（硬编码，不在 `category_rule` 表）：

   | 条件（merchant）                                 | 分类                                |
   | ------------------------------------------------ | ----------------------------------- |
   | 以 `ATM` 开头                                    | 现金支出（system: cash_withdrawal） |
   | 含 `ACCOUNT SERVICING FEE`（包括 `REVERSAL OF`） | 银行费用（system: bank_fee）        |

   其他银行费用（如信用卡利息）等拿到对应 CSV 后再加，不提前猜。

3. 用户规则（`category_rule` 表）：
   - 对 merchant 做匹配：`contains` 是包含，`starts_with` 是开头匹配，都不区分大小写
   - 多条命中时：`priority` 大的优先；相同时**关键词长的优先**（`DOWNTOWN GROCER` 优先于 `GROCER`）；再相同按创建时间早的
4. 都没命中 → 未分类（system: uncategorized）

`category_source`：1、2 写 `system`，3 写 `rule`，用户手动改的写 `manual`。

`is_pre_tax`：分类确定后，等于该分类的 `is_pre_tax_default`。用户可以单独改；之后分类再变时重新按分类设置。

### R7.1 正数金额（退款、报销）

- 正数交易同样走上面的规则
- 命中支出类规则（如 `MELB ASIAN MARKET` +0.72）→ 归到那个支出分类，在统计里**冲减**该分类支出（见 R10）
- 没命中 → 未分类，由用户决定是收入还是退款

### R7.2 重新应用规则

用户新建或修改规则后，可以选择对已有交易重新分类：

- **只改 `category_source = rule` 或未分类的交易**
- `manual` 和 `system` 的不动
- 分类变了的，按 R5.1 重新计算归属人
- **有多个拆分的交易跳过**，只处理只有一个拆分的交易
- 提示的"跳过几笔"只算本来会被考虑（有 `rule` 来源或未分类的拆分）、因为多个拆分被跳过的交易；全是 `manual` 的多拆分交易本来就不会动，不算（2026-10-24 补）

## R8. pending 交易匹配

### R8.1 手动录入时

| 账户                                            | status    | 原因                  |
| ----------------------------------------------- | --------- | --------------------- |
| bank = cash、anz_plus、other（没有 CSV 解析器） | confirmed | 不会有银行流水来确认  |
| bank = anz、cba                                 | pending   | 等导入 CSV 时匹配确认 |

ANZ Plus 只能看 PDF 对账单，利息每月手动记一笔（Income / Interest，税前），录入后直接 confirmed。

日期默认今天（`Australia/Melbourne`）。手动录入的交易没有 `dedupe_key`。

### R8.2 导入时匹配

对每笔通过去重检查（R4）的 CSV 行，在同账户的 `pending` 交易里找候选：

- `amount_cents` 完全相等
- CSV 日期 − pending 日期 ∈ [0, 3] 天（银行入账不会早于消费）
- 还没被本次导入的其他行匹配走

| 候选数 | 处理                                                 |
| ------ | ---------------------------------------------------- |
| 0      | 正常插入新交易                                       |
| 1      | **确认这笔 pending，不插入新交易**（见 R8.3）        |
| ≥ 2    | 正常插入新交易，两边都提示"可能重复"，让用户手动处理 |

### R8.3 确认时更新的字段

| 字段                                     | 处理                             |
| ---------------------------------------- | -------------------------------- |
| status                                   | → confirmed                      |
| date                                     | → 银行日期                       |
| raw_description、merchant、card_last4    | → 银行的                         |
| dedupe_key、import_batch_id              | → 填上                           |
| confirmed_at                             | → now()                          |
| 拆分（分类、归属人、note，包括多个拆分） | **保留用户录入的**，不用规则覆盖 |
| source                                   | 保留原来的（`manual`，或小票建的 `receipt`，R20.7） |

**例外：银行那行是内部转账。** 确认时对银行那行跑 R6.1，认出是内部转账时 R6.1 优先：

- `transfer_status = auto`，主拆分分类改成内部转账，`category_source = system`
- 归属人按 R5.1（手动录入的是 `manual`，不动），备注保留
- pending 有多个拆分时不改，保留用户的拆分，在 F8 提示
- 之后照常参加 R6.2 配对

理由：手动录入时多半没想到这是转给自己的账户，按银行信息纠正更合理。转给朋友的钱 R6.1 认不出，不受影响。

### R8.4 导入后提示

导入完成后，该账户里日期 ≤ 本次 `date_to` − 3 天、仍是 pending 的交易 → 在导入结果页列出，提示检查。

## R9. 对账校验

有期初和期末余额时（ANZ 的 CSV 由用户手动填，ANZ 的 PDF 对账单从汇总页读（R1C），CBA 按 R1B.2 自动得出）：

```
opening_balance + Σ(该账户所有 confirmed 交易，date ∈ [date_from, date_to]) == closing_balance
```

- 用**数据库里**的交易合计，不只是本次文件（能发现之前漏导的）
- pending 不算
- 相等 → `reconciled = true`；不等 → `false`，显示差额

## R10. 统计口径

所有统计基于 `transaction_split`，按**交易的 `date`** 归入时间段。

| 指标     | 计算                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 收入     | Σ 拆分金额，分类 kind = `income`。包括 Tax (ATO) 的负数，所以交了税收入会变少；其中税前部分单独显示"其中税前 $X" |
| 支出     | −Σ 拆分金额，分类 kind = `expense`，**加上**系统分类"现金支出"、"银行费用"                                       |
| 不计入   | 系统分类"内部转账"（`transfer_status` 为 `auto` 或 `confirmed`）；"未分类"单独显示，不计入收支                   |
| 储蓄率   | (收入 − 支出) ÷ 收入；收入为 0 时显示"—"                                                                         |
| 分类支出 | 二级汇总到一级；退款（正数）直接冲减，所以某分类可能是负数，照实显示                                             |
| pending  | 计入统计，界面上可区分显示                                                                                       |

例子：本月 Groceries 有 −120.00 和 +0.72（退款）→ Groceries 支出 = 119.28。

"未分类"不计入收支是为了逼自己去处理它，看板上显示未分类的笔数和金额，点进去到 F8。

**已知局限**：税前收入在年底交税前会让储蓄率偏高。看板上同时显示 R14 的"预计年底补税"，自己心里有数。

### R10.1 时间段

| 选项   | 范围                                                        |
| ------ | ----------------------------------------------------------- |
| 本周   | 本周一到今天                                                |
| 上周   | 上周一到上周日                                              |
| 本月   | 本月 1 日到今天                                             |
| 上月   | 上月 1 日到上月最后一天                                     |
| 本季度 | 自然季度第一天到今天                                        |
| 今年   | 1 月 1 日到今天                                             |
| 本财年 | 7 月 1 日到今天（今天在 1 到 6 月时，从去年 7 月 1 日开始） |
| 自定义 | 用户选起止日期，含首尾                                      |

"今天"按 `Australia/Melbourne`。对比时用上一个同长度时间段（本月 1 到 21 日对比上月 1 到 21 日）。

### R10.2 汇总表

在选定时间段内，按时间粒度切分，再按一个维度分组求和。

| 参数 | 选项                             |
| ---- | -------------------------------- |
| 粒度 | 按周 / 按月                      |
| 分组 | 分类（一级，可展开二级）/ 归属人 |
| 指标 | 支出（默认）/ 收入               |

- 周从**周一**开始，到周日结束
- 时间段首尾不满一周或一个月的，只算时间段内的日子，表头标"部分"（如 `9/1–9/6 部分`）
- 每格金额按 R10 口径；行合计、列合计都显示
- 格子不跳 F8：按分类分组时，点一级那一行（名字或任意格子）展开或收起二级；其他行点了没反应（2026-10-25 改）

例子：`joint-2026-09.csv`，时间段 2026 年 9 月，按周，支出合计：

| 周                | 支出(分) |
| ----------------- | -------- |
| 9/1–9/6（部分）   | 5840     |
| 9/7–9/13          | 8580     |
| 9/14–9/20         | -705     |
| 9/21–9/27         | 21120    |
| 9/28–9/30（部分） | 10740    |
| 合计              | 45575    |

9/14 那周是负数：Medicare 报销 +45.80 大于当周支出 38.75，照实显示。

### R10.3 Top 商家（2026-10-24）

在选定时间段内，按 `transaction.merchant` 分组，**按笔数**排。

- 只看 R10 支出口径的拆分（支出类分类，加上现金支出、银行费用）
- 一笔交易算一次：先把这笔交易里命中的支出拆分加起来
  - 合计是负数（花了钱）→ 笔数 +1，金额加上它
  - 合计是正数（退款）→ 不算笔数，只冲减金额
- 笔数是 0 的商家不列（只有退款的，如 MEDICARE BENEFIT）
- 排序：笔数多的在前；笔数一样按金额大的在前；再一样按商家名字母顺序
- 显示前 5 个：商家名、笔数、金额

例子：`MELB ASIAN MARKET` 有 -62.30 和 +1.50（退款）→ 1 笔，$60.80。

### R10.4 对比上期（2026-10-24）

上期按 R10.1 的规则取上一个同长度时间段。

| 指标 | 显示 | 例子 |
| --- | --- | --- |
| 收入、支出 | 百分比变化 = (本期 − 上期) ÷ 上期，四舍五入到整数 | 上期 400.00、本期 455.75 → `+14%` |
| 储蓄率 | 百分点差 = 本期 − 上期，四舍五入到整数 | 上期 21.8%、本期 25.0% → `+3 pp` |
| 未分类 | 不对比 | |

- 上期 ≤ 0（收入、支出），或任一期储蓄率是"—"，显示"—"
- 四舍五入按绝对值，再带上符号：-12.5% → `-13%`
- 涨跌都用灰色，不用红绿（支出涨不一定是坏事）

### R10.5 近 12 个月趋势（2026-10-24）

- 固定是含本月在内的近 12 个自然月，本月只到今天。**不跟**时间段选择走
- 每月：收入、支出（R10 口径）、净额 = 收入 − 支出
- 没有数据的月份显示 0，不跳过

例子：今天 2026-10-24 → 2025-11-01 到 2026-10-24，最后一段是 2026-10-01 到 2026-10-24。

### R10.6 看板的归属人筛选和 pending（2026-10-24）

- pending 交易照常计入，看板上显示"含 N 笔待确认交易"：N 是时间段内、有拆分命中当前归属人筛选的 pending 交易笔数

## R12. 导入流程（一次事务）

```
1. R1 解析整个文件            失败 → 报错，什么都不写
   CBA：R1B.1 余额检查（只记警告）、R1B.2 得出期初期末
   ANZ PDF：R1C 的检查（不过就失败）、期初期末从汇总页来；import_batch 的 date_from = 账期开始日的第二天，date_to = 账期结束日（R1C）
2. 对每行：R2 提取脱敏 → R3 清洗 → R4 生成 key
3. 开启事务
4.   创建 import_batch
5.   对每行：
       已存在 key → 计数跳过
       R8 找 pending → 确认（R8.3，含 R6.1 例外）或插入新交易
       新交易：R6.1 转账 → R7 分类和 is_pre_tax → R5 归属人 → 写 transaction（CBA 带 balance_cents）+ 一行主拆分（is_primary = true）
6.   R6.2 配对（整个家庭）、R6.3 兜底建议
7.   R9 对账（有余额时）
8.   更新 import_batch 计数
9. 提交事务                   任意一步出错 → 全部回滚
10. 返回结果：新增、跳过、确认 pending、未分类数、待检查 pending、对账结果、余额警告
```

### R12.1 撤销导入

- 按 `import_batch` 撤销：删除该批次插入的交易（拆分级联删除）
- **每个账户只能撤销最近一次导入**。更早的批次如果和后面的批次日期重叠，重叠的行在后面那次被当成重复跳过了，撤销早的会让这段数据变空
- 被该批次确认的 pending → 恢复成 pending，清空 dedupe_key、import_batch_id、confirmed_at（日期、描述恢复不了，保留银行的；被 R8.3 例外改成转账的，分类也恢复不了）
  - 被 R8.3 例外改成转账的，`transfer_status` 保持 `auto`，只清空 `transfer_pair_id`。手动录入时一般不会记内部转账，这种情况很少见；保持 auto 的话，之后的 R6.2 或重新导入都能把它重新配上

**撤销前弹窗提醒**：批次里有手动改过的交易（`category_source` 或 `member_source` 是 `manual`、有多个拆分、有备注、挂了小票），或者有被确认的 pending 时，列出各有几笔，用户确认后才撤销。都没有就直接撤销。被删的交易挂的小票会脱开，见 R20.7（2026-10-27 补）

**和别的交易的配对**：被删的交易、恢复成 pending 的交易，如果和别的交易配了对（`transfer_pair_id`），先处理对方再删：

| 对方的情况                                                         | 处理                                                                       |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| `transfer_status = none`（R6.2 配对时它是 manual 分类，没改）      | 只清空 `transfer_pair_id`                                                  |
| `suggested` 或 `confirmed`（R6.3 来的）                            | 清空配对，`transfer_status = none`，分类改回未分类，`category_source = system` |
| `auto`，用它自己的描述重跑 R6.1 还能认出                           | 保持内部转账，只清空配对，等重新导入时再配上                               |
| `auto`，重跑 R6.1 认不出（当初是 R6.2 改的，如 CBA 的 PayID 转账） | 同第二行，改回未分类                                                       |

- 改回未分类的，按 R5.1 重算归属人
- 重跑 R6.1 用的是数据库里**脱敏后**的描述，完整账号已经没了：`****1234` 当成 4 位尾号，按 CBA 的方式匹配（家庭账户的尾号以这 4 位结尾）。前面带 BSB 的 `012345-****1234` 一样取 `1234`（R2.2）
- 先清空配对再删交易，所以 `transfer_pair_id` 的外键不用改

### R12.2 防漏导（2026-10-28 新增）

ANZ 的 CSV 要自己选时间段，又没有余额，容易漏一段。三层提示，都**不拦**导入：

**导入前：建议从哪天开始导出**

选了账户后显示"上次导入到 X"，X = 这个账户所有导入批次里最大的 `date_to`（CSV 是文件里最晚的交易日期，PDF 是账期结束日）。

- 建议导出范围：X − 7 天 到今天。故意往前重叠一周：晚入账的交易会补上，重复的由 R4 跳过
- 这个账户还没导入过：不显示

**导入后：和上次之间可能有空档**

**只对 CSV 批次**：本次 `date_from` > 上次的 X（和以前的导入没有重叠）→ 结果页警告"这次最早是 A，上次导到 X，中间可能漏了，下次导出往前多选几天"。

CSV 的 `date_from` 是第一笔交易的日期，中间几天正好没交易也会触发，所以只是提醒。真正确定有没有漏，靠 PDF 对账单（R1C + R9）。PDF 批次不做这个检查（它的 `date_from` 是账期开始日的第二天，和上一份对账单的 `date_to` 永远差一天），用下面的首尾衔接。

**PDF 对账单：首尾衔接**

导入 PDF 时找这个账户上一份 PDF 批次（`source = pdf`，`date_to` 最大的、早于本次的）：

| 情况 | 结果页 |
| --- | --- |
| 上一份的期末 = 本次的期初 | "和上一份对账单（A 到 B）接上了" |
| 余额对不上 | 警告"和上一份对账单之间余额对不上，差 $X，可能中间少了一份对账单" |
| 没有上一份 | 不提示 |

导入页还显示"对账单已经导到 B"，提醒下一份该从 B 开始。

## R14. 税后估算

**只是估算，不是税务建议。** 没有算业务开支抵扣、各种 offset、Medicare levy 低收入减免，所以结果偏保守（偏高）。实际以 ATO 和会计为准。

B2B 收入不含 GST（没有注册），到账金额全额算税前收入。

代码放 `src/lib/tax/`，纯函数。

### R14.1 财年

- 7 月 1 日到次年 6 月 30 日，用开始年份表示：`2026` = 2026-27
- 交易按 `date` 归入财年

### R14.2 每人的税前收入

对每个 kind = person 的归属人，在一个财年内：

```
preTaxIncome = Σ 拆分金额（is_pre_tax = true，member = 这个人）
             + Σ 拆分金额（is_pre_tax = true，member kind = shared）÷ person 人数
```

- Home 名下的税前收入（如 joint account 的利息）在所有 person 之间平分，报税时一般就是这样分
- 平分除不尽的分，余数给排序靠前的人

### R14.3 计算

```
taxable   = payg_gross + preTaxIncome          （来自 tax_profile，没有记录时 payg 为 0）
incomeTax = 按当年税率表分档计算(taxable)
medicare  = taxable × 2%
total     = incomeTax + medicare
prepaid   = −Σ Tax (ATO) 分类里该人的负数拆分（只算负数，退税不算）
owing     = total − payg_withheld − prepaid    （负数表示预计退税）
```

- `taxable` 先向下取整到整元，再按分档算
- 结果四舍五入到分

### R14.4 税率表（resident，不含 Medicare levy）

写在 `src/lib/tax/rates.ts`，按财年存。新财年的税率要手动加，没有该财年的表时报错，不要沿用旧表。

| 应纳税收入          | 2025-26 | 2026-27 |
| ------------------- | ------- | ------- |
| $0 – $18,200        | 0%      | 0%      |
| $18,201 – $45,000   | 16%     | 15%     |
| $45,001 – $135,000  | 30%     | 30%     |
| $135,001 – $190,000 | 37%     | 37%     |
| $190,001 以上       | 45%     | 45%     |

2027-28 起第二档降到 14%，其他档开工时再确认后加入。

### R14.5 例子（2026-27）

| 场景          | payg_gross | 税前收入 | taxable | incomeTax | medicare | total  |
| ------------- | ---------- | -------- | ------- | --------- | -------- | ------ |
| A：工资 + B2B | 60,000     | 30,000   | 90,000  | 17,520    | 1,800    | 19,320 |
| B：B2B 跨档   | 40,000     | 10,000   | 50,000  | 5,520     | 1,000    | 6,520  |
| C：只有 B2B   | 0          | 30,000   | 30,000  | 1,770     | 600      | 2,370  |

场景 A 算 owing：假设 payg_withheld = 9,720（正好是 60,000 工资单独的税），已预缴 900 → owing = 19,320 − 9,720 − 900 = **8,700**。

场景 B 说明为什么不能用"税前收入 × 边际税率"：10,000 的 B2B 实际多出 2,450 的税（一半在 15% 档、一半在 30% 档，加 2% Medicare），用 32% 直接乘会得到 3,200。

场景 D：Home 名下有 100.00 利息，Male 和 Female 各算 50.00。

### R14.6 显示

- 没有填 tax_profile 时提示去设置页填，仍然按 payg 为 0 计算

## R15. 简单拆分

### R15.1 结构

- 每笔交易至少一个拆分，恰好一个 `is_primary = true`（主拆分）
- 导入和手动录入时只建主拆分
- 所有拆分 `amount_cents` 合计永远等于交易的 `amount_cents`

### R15.2 拆出一部分

输入：交易、金额（用户填正数，按交易符号转换）、分类、可选归属人、可选备注

校验：

- 金额 > 0
- 金额 < 主拆分当前金额的绝对值（主拆分不能变成 0 或反号）

执行（一个事务）：

1. 主拆分 `amount_cents` 减去这部分
2. 新建拆分：同符号金额，`is_primary = false`，`category_source = manual`
3. 归属人：用户选了就用，`member_source = manual`；没选就对新拆分按 R5 计算（分类默认 > 卡号 > 账户）
4. `is_pre_tax` 按新分类的默认值

补充（2026-10-24）：

- 新拆分的分类按 R16.3 的可选范围校验
- `transfer_status` 为 `auto` 或 `confirmed` 的交易不能拆分（R16.2：分类不能改）。`suggested` 的可以拆，但拆了以后不能确认（R6.3）
- 备注去掉首尾空格，最长 200 字符，空的存成没有

### R15.3 修改和删除

- 改非主拆分的金额：差额从主拆分补或扣，同样要满足 R15.2 的校验
- 删除非主拆分：金额全部加回主拆分
- 主拆分不能删除，可以改分类和归属人
- 交易只剩主拆分时，就是普通交易
- 一次修改里同时改金额、分类、归属人、备注时，任何一项不通过都整体不改；分类和归属人一起改时，先按 R16.4 改分类（R5.1 重算），再把归属人设成手动指定的（2026-10-24 补）

### R15.4 和其他规则的关系

- 统计（R10、R10.2、R11、R14）本来就按拆分算，不用改
- 规则重新应用（R7.2）跳过有多个拆分的交易
- pending 确认（R8.3）保留所有拆分；如果银行金额和 pending 金额不同不会匹配，所以合计不变
- 撤销导入（R12.1）删除交易时拆分级联删除

### R15.5 例子

`joint-2026-09.csv` #19：COLES -58.40，主拆分 Groceries / Supermarket，Home。

| 操作                                                                  | 主拆分                 | 其他拆分                                                   |
| --------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------- |
| 拆出 15.00 → Home & utilities / Household supplies，不选归属人        | -43.40                 | -15.00 Household supplies，Home（category）                |
| 再拆出 8.00 → Personal & medical / Cosmetics & toiletries，不选归属人 | -35.40                 | 加一行 -8.00 Cosmetics & toiletries，**Male（card 1111）** |
| 拆出 50.00                                                            | 报错：超过主拆分 35.40 |                                                            |
| 删除 Cosmetics 那行                                                   | -43.40                 | 只剩 Household supplies                                    |

## R16. 流水查询里的修改（F8，2026-10-24 新增）

### R16.1 多拆分交易

一笔交易像一张小票，拆分是小票里的一部分商品（按分类 + 归属人分堆，不是每件商品一行）。

- 只有主拆分的交易：列表里一行，行内直接改分类、归属人
- 有多个拆分的交易：主行显示"已拆分 N"，**主行不能改**；下面展开成子行，每个拆分一行，各自改分类、归属人
- 拆分的金额、新增、删除只在交易详情里做（R15.2、R15.3）
- 批量修改**跳过**有多个拆分的交易，结果里提示跳过了几笔
- 批量修改的结果（2026-10-24 补）：
  - "改了"包括值本来就一样、实际没变的；"跳过"只算本节和 R16.2 跳过的
  - 选中的交易有一笔找不到（比如已经撤销导入），整批报错、一笔都不改，提示刷新
  - 一次最多 200 笔（列表一页的上限）

### R16.2 转账行

- `transfer_status` 为 `auto` 或 `confirmed` 的交易，分类**不能改**，只能改归属人
- 批量修改改分类时跳过这些交易，计入"跳过"。同时改分类和归属人时也整笔跳过，归属人也不改（2026-10-24 补）
- `suggested` 的交易分类是未分类，可以照常改；改了以后仍是 `suggested`，确认或拒绝按 R6.3

### R16.3 分类下拉的可选项

| 分类 | 能不能选 |
| --- | --- |
| 所有 expense、income 分类（一级和二级，归档的除外） | 能 |
| 系统分类：未分类、现金支出、银行费用 | 能 |
| 系统分类：内部转账 | **不能**。转账只能由 R6.1 识别、R6.2 配对或 R6.3 确认产生 |

一级分类归档后，它下面的二级也不能选，即使二级自己没归档（2026-10-24 补）。

### R16.4 手动改分类和归属人

- 改分类：`category_source = manual`，`is_pre_tax` 按新分类的默认值（R7），归属人按 R5.1 重算
- 改归属人：`member_source = manual`

### R16.5 筛选

**类型**按 R10 的分类口径，不看金额正负：

| 类型 | 条件（拆分的分类） |
| --- | --- |
| 收入 | kind = `income` |
| 支出 | kind = `expense`，加上现金支出、银行费用 |
| 内部转账 | 内部转账 |
| 未分类 | 未分类 |

所以 MEDICARE BENEFIT +45.80（Personal & medical / Other）算"支出"类型。

**合计**：

- 列表一笔交易一行，只要有一个拆分命中筛选条件就列出
- 筛选条件里有分类、归属人、类型或是否税前时，合计**只加命中的拆分**，和 R10 统计一致
- 只按交易本身的字段（时间、账户、状态、商家、金额范围）筛选时，合计就是交易金额之和
- 金额范围按**交易**金额比较，不按拆分

例子：拆分用例做完后（#19 主拆分 -35.40 Supermarket，另两个拆分 -15.00、-8.00），筛选 Groceries / Supermarket，#19 列出，合计里只算 -35.40。

### R16.6 存规则时关键词已经存在

`(keyword, match_type)` 在本家庭唯一。已经有同样的规则时：

- 指向的分类相同 → 什么都不做，直接进入"是否应用"（R7.2）
- 指向不同分类 → 对话框提示"已有规则 COLES → Groceries / Supermarket"，确认后把这条规则改成新分类（预置规则也可以改），再问是否应用

### R16.7 R6.2 只配对不改的交易

R6.2 里另一半分类是 `manual`、只配对没改的交易（有 `transfer_pair_id`，`transfer_status = none`），列表里显示小标签"已配对，分类是手动的"，不做单独筛选。

### R16.8 可能重复的 pending

R8.2 候选 ≥ 2 时写进 `import_batch.warnings` 的可能重复，在 F8 里提示放到 **M6** 做（M6 之前录不进 pending）。具体怎么判断见 R17.6。

### R16.9 什么时候弹"存成规则"（2026-10-24 补）

改完分类后，下面三条都满足才弹 R13 的"存成规则"对话框：

- 分类真的变了（选了原来的分类不弹）
- 新分类是 expense 或 income。改成未分类、现金支出、银行费用不弹
- 改的是主拆分。多拆分交易的子行不弹，因为规则按整笔交易的商家匹配
- 有类似交易：本家庭**除了这笔以外**，还有交易的 merchant 包含建议的关键词（R13，不区分大小写，不管它现在是什么分类）（2026-10-25 补）

前三条满足、第四条不满足时（这个商家目前只有这一笔），不弹对话框，改分类的 toast 里带一个"存成规则"按钮，点了打开同一个对话框。规则主要是给以后导入用的，所以入口留着，只是不打断。

例子（joint）：把 #14 MELB ASIAN MARKET 改成 Groceries / Asian grocer → #13 也含 `MELB ASIAN MARKET`，弹。把 #15 UNKNOWN SHOP PTY LTD MELBOURNE 改成 Shopping → 只有它自己，不弹，toast 里有"存成规则"。

从这个对话框存的规则，匹配方式固定是 `contains`，对话框里不让选。


### R16.10 改归属人后同商家一起改（2026-10-25）

在 F8 列表里改了一笔交易主拆分的归属人后（行内改，不含批量修改和详情页的拆分），看有没有同商家的交易要一起改：

- 范围：本家庭除了这笔以外，merchant 包含这笔建议关键词（R13 的 `suggestKeyword`，不区分大小写）的交易
- 只算：只有主拆分、归属人不是新选的人、`member_source` 不是 `manual`（用户以前手动定过的不动）、`transfer_status` 不是 `auto` 或 `confirmed`
- 有 ≥ 1 笔 → 弹窗"商家含 X 的还有 N 笔归属人不是 Y，要一起改吗？"，确认后这些都改成 Y，`member_source = manual`，一个事务
- 0 笔不弹
- 只改已有的。以后导入的同商家交易还是按 R5 算，要长期生效就改分类的默认归属人（R19）
- 同一次操作里分类也改了时，先走 R16.9 存规则，再问这个

例子（joint）：#4 GONG CHA 改成 Female → #5 也含这个商家、是 Male（card）→ 弹窗 N = 1，确认后 #5 变成 Female（manual）。

## R17. 手动录入（F3，2026-10-25 新增）

R8.1 定了状态，这里补表单和编辑删除的规则。

### R17.1 字段

| 字段 | 规则 |
| --- | --- |
| 金额 | 必填，> 0，最多两位小数，用 `parseSplitAmountInput` 的口径转整数分；按"支出 / 收入"切换定符号（支出负、收入正） |
| 描述 | 必填，去掉首尾空格，最长 100 字符。`raw_description` 存去空格后的原文，`merchant` = R3 清洗结果（大写），和导入的商家能合到一起统计 |
| 账户 | 本家庭没归档的账户都能选，包括能导入 CSV 的（R8.1：ANZ、CBA 记成 pending） |
| 日期 | 默认今天（`Australia/Melbourne`），不能晚于今天，往前不限 |
| 分类 | 可以不选，不选就是未分类。可选项是 R16.3 的下拉再按切换过滤：支出 → expense 分类加现金支出、银行费用；收入 → income 分类 |
| 归属人 | 默认"自动"，见 R17.3 |

- 不录备注，备注在交易详情里改
- `card_last4`、`balance_cents`、`dedupe_key`、`import_batch_id` 都是空，`transfer_status = none`，`source = manual`，`created_by` = 当前用户
- 只建主拆分（R15.1），`is_pre_tax` 按分类默认（R7）
- 录入时**不跑** R6.1，手动录入不会自动变成内部转账（导入确认时的例外见 R8.3）

### R17.2 猜分类、常用分类、上次账户

**猜分类**：描述改变时，对清洗后的 merchant 跑 R7 第 2、3 步（系统规则、用户规则），命中就预选，标"猜的"。

- 用户已经自己点过分类，就不再用猜的覆盖
- 猜出来的分类类型和当前切换不一致（如切换在"收入"，猜出 Coffee & tea），当作没猜到
- 没命中 → 不预选（保存时是未分类）

**常用分类**：本家庭 `source = manual` 的交易里，最近 90 天主拆分用过的分类，按次数从多到少，次数一样按最近一次用的时间。只显示和当前切换同类型的前 4 个，后面是"更多…"，打开 design/README 第 3 节的分类下拉。没录过几笔、不够 4 个时就少显示几个，不补。

**上次账户**：当前用户最近一笔 `source = manual` 交易（按 `created_at`）的账户。从数据库取，换设备也一样；那个账户归档了或者从来没录过，就不预选，让用户选。

### R17.3 分类和归属人的来源

| 情况 | category_source | member_source |
| --- | --- | --- |
| 用了猜的分类，用户没动 | `rule` | — |
| 用户自己选了分类 | `manual` | — |
| 没选分类（未分类） | `system` | — |
| 归属人是"自动" | — | 按 R5 算：分类默认 > 账户默认（没有卡号），记 `category` 或 `account` |
| 用户自己选了归属人 | — | `manual` |

表单上"自动"旁边实时显示 R5 算出来的人，用户一眼能看到会记给谁。这样以后改规则（R7.2）、改分类（R5.1）还能照常更新没被用户动过的字段。

### R17.4 保存并再记一笔

保存后表单留着，保留账户、日期、支出 / 收入切换；清空金额、描述、分类，归属人回到"自动"，重新聚焦金额。

### R17.5 编辑和删除整笔交易

只有 `source = manual`（或小票建的 `source = receipt`，R20.7）**且** `import_batch_id` 为空的交易能编辑、删除整笔（还没被导入确认的 pending，以及现金、ANZ Plus 这类直接 confirmed 的）。被导入确认过的 pending（R8.3）和导入的交易一样，只能改分类、归属人、拆分、备注。

**编辑**：日期、金额、描述、账户，规则同 R17.1。

- 不能改符号（支出改收入）。要改就删掉重记
- 改金额：只有主拆分时才能改，主拆分跟着变；有多个拆分时提示先删掉拆分
- 改描述：重新清洗 merchant，**不**重新猜分类、不动分类
- 改账户：状态按新账户重新走 R8.1（ANZ → 现金变 confirmed，现金 → ANZ 变 pending）；归属人如果不是 `manual`，按 R5 用新账户重算
- 改日期、金额、账户以后，这笔 pending 在以前导入批次 `warnings` 里的"可能重复"不会自己消失，按 R17.6 实时算

**删除**：硬删除（tech-stack：交易只限手动录入的能硬删），拆分级联删除。删除前弹窗确认。

- 有 `transfer_pair_id` 的不能删（R6.3 可能把未分类的手动录入建议成转账），提示先在 F8 拒绝建议

### R17.6 可能重复的 pending（补 R16.8）

R8.2 候选 ≥ 2 时，导入批次 `warnings.possibleDuplicates` 记了 `{ transactionId, pendingIds }`。F8 里实时判断，不另存状态：

- 对每条记录，`pendingIds` 里**还存在且还是 pending** 的那几笔，加上 `transactionId`，都显示"可能重复"标签
- 还剩 0 笔 pending → 这条记录不再提示，银行那笔也不显示
- 用户的处理方式就是删掉或改掉多余的 pending（R17.5），没有"忽略"按钮，不改 `warnings`
- 撤销那次导入（R12.1）后批次没了，提示跟着消失

例子（fixtures P3、P4）：导入 joint 后，#12 和 P3、P4 都显示"可能重复"。删掉 P4 → P3 和 #12 还显示（P3 仍是 pending）。再删掉 P3 → 都不显示。

## R18. 规则管理（2026-10-25 新增）

设置 → 规则（`/settings/rules`），能看到本家庭所有分类规则，新建、修改、删除。预置规则（`is_system = true`）和自己建的一样处理，只多一个"预置"标签。

### R18.1 列表

| 列 | 内容 |
| --- | --- |
| 关键词 | 大写 |
| 匹配方式 | 包含（`contains`）/ 开头是（`starts_with`） |

- **命中**：本家庭的交易如果现在重跑 R7，有几笔会用到这条规则（这条规则在 R7 第 3 步胜出）。只看 merchant，不管交易现在是什么分类、来源是什么。内部转账（`transfer_status` 为 `auto` 或 `confirmed`）和命中系统规则（R7 第 2 步）的不算

- 匹配方式是"包含"的，命中数能点，跳 F8 带商家筛选 = 关键词（F8 商家筛选也是包含，R16.5）。"开头是"的不能点，F8 没有开头匹配，点过去数字会对不上
- F8 里列出的笔数可能比命中数多：被更长关键词抢走的、内部转账、命中系统规则的商家名里也有这个词。命中数旁边（悬停或小字）写"F8 按商家搜索，笔数可能更多"，F8 不加"按规则筛选"（2026-10-26 补）

### R18.2 新建和修改

- 字段：关键词、匹配方式、分类。`priority` 不在界面上改，新建的是 0
- 关键词按 R13 处理：去首尾空格、多个空格合成一个、转大写，最长 100 字符，不能为空
- 分类的可选范围同 R16.3（内部转账、归档的不能选）
- `(keyword, match_type)` 在本家庭唯一。和别的规则撞了就报错"已有规则 X → Y"，不合并，让用户去改那一条。改的是自己这条且关键词没变，不算撞
- F8 弹窗存的规则仍然固定是"包含"（R16.9），只有这个页面能选"开头是"
- 修改预置规则后 `is_system` 不变，还显示"预置"标签（2026-10-26 补）

### R18.3 删除

- 删除前弹窗确认，写明命中几笔
- 删除只删规则，**不动**已经分好类的交易（它们的 `category_source` 还是 `rule`）

### R18.4 新建、修改、删除之后

和 R13 一样，问"要对 N 笔应用吗"，N 是 R7.2 的预览数。选应用就按 R7.2 重跑：

- `rule` 来源和未分类的交易整套重跑 R7。删掉的规则、改掉的关键词不再命中，又没有别的规则命中 → 变回未分类
- `manual`、多拆分的照 R7.2 不动

例子：有规则 `CAFE` → Coffee & tea，`BLUE CAFE BAR` 被它分成 Coffee & tea（`rule`）。

| 操作 | 不应用 | 应用 |
| --- | --- | --- |
| 删除 `CAFE` | 还是 Coffee & tea | 变回未分类 |
| `CAFE` 改成 `BLUE CAFE` | 还是 Coffee & tea | 还是 Coffee & tea（新关键词仍命中） |
| `CAFE` 的分类改成 Restaurants | 还是 Coffee & tea | 变成 Restaurants，归属人按 R5.1 重算 |

### R18.5 预置规则和 seed

seed 脚本**只在本家庭还没有分类时**插分类和预置规则（第一次 seed），见 R19.5。之后再跑 seed 不碰 `category_rule`，管理页里删掉或改过的预置规则不会被加回来。

以后 `seed-categories.md` 加了新的预置规则，已有的家庭要在管理页手动建。

## R20. 小票识别（2026-10-27 新增）

拍一张小票（或粘贴识别出来的文字），按分类拆到对应的交易上（F10 / R15）。分工：

- **读小票**由一个可以替换的 reader 做（R20.1），有用 AI 的和不用 AI 的，用哪个由配置决定。reader 只负责把小票变成统一格式的原始结果，商品分类也只是建议，用户在核对界面确认或改
- **钱的计算全部是纯函数**：金额转换、合计校验、折扣分摊、拆分、匹配（R20.2 到 R20.5），和用哪个 reader 无关，能写测试，每次结果一样
- reader 失败（LLM 停了、额度用完、格式不对、文字解析不出来）：核对界面显示"暂时识别不了"，商品表是空的，可以手动填，其他功能不受影响

### R20.1 reader 和原始结果

**原始结果**（所有 reader 返回同一个格式，Zod 校验，不通过当作识别失败）：

| 字段 | 内容 |
| --- | --- |
| merchant | 店名，原样 |
| date | 小票日期，原样字符串（如 `24/10/2026`、`24/10/26`），由 R20.2 转换 |
| total | 总额，原样字符串（如 `46.12`、`$46.12`） |
| items | `[{ name, amount, category }]`。`amount` 原样字符串，单件折扣是负数；`category` 是分类列表里的一个字符串，或 `null`（跟主分类，见 R20.3） |
| discounts | 整单折扣 `[{ label, amount }]`，`amount` 是负数字符串。没有就是空数组 |
| payment | `{ method: card / cash / unknown, cardLast4: 4 位数字或 null }` |

不管哪个 reader，原始结果里都**没有人名**（顾客、收银员、店长）、终端号、ABN、电话，多出来的字段 Zod 直接丢掉。`cardLast4` 只在内存里给 R20.4、R20.5 用，**不入库**，不写进 `parsed_json`，也不写进交易的 `card_last4`。**图片不保存**，粘贴的文字也不保存，只存 R20.2 整理后的结果。

**reader**（配置 `RECEIPT_READER` 选一个，tech-stack 11.3）：

| reader | 输入 | 用 AI | 分类建议 |
| --- | --- | --- | --- |
| `llm` | 照片 | 是，OpenAI 兼容接口的看图模型，换服务商只改环境变量 | 有 |
| `text` | 粘贴的文字（手机自带的识别文字功能复制出来的） | 否，确定性解析（R20.1b） | 没有，都是 `null` |
| `none` | 无 | 否 | 没有。直接打开空的商品表手动填 |

以后加别的（比如浏览器里本地 OCR），只要返回同样的原始结果就行，R20.2 以后不用改。

### R20.1a `llm` reader

**发出去**：一张图片（浏览器里先压缩成 JPEG，长边不超过 1600px、不超过 1MB），加上本家庭能选的支出分类列表（R16.3 范围内 kind = expense 的二级，格式 `一级 / 二级`）。不发账户、交易、金额、日期，不发其他任何数据。

提示词要求：

- 称重、数量明细行（`0.581 kg NET @ $4.90/kg`、`4 @ $1.70 EACH`）不算商品
- 单件折扣（`GOLD KIWIFRUIT 4 FOR $6 -$0.80`）作为负数商品，紧跟在被折扣的商品后面
- 整单折扣（`DISCOUNT -$2.04`）放 `discounts`，不放 `items`
- GST、付款方式、找零、积分行不算商品
- 不返回人名、终端号、ABN、电话
- 食品类商品 `category` 给 `null`，只有明显不属于这家店主分类的（日用品、化妆品、药、酒等）才给分类

**隐私**（prd 第 4 节"AI 功能"的例外）：小票图片里有金额、日期、店名，可能还有卡号后 4 位和人名，整张图会发给服务商，没法只发一部分。所以只用不拿数据训练的服务商（tech-stack 11.1）。不想发图就用 `text` 或 `none`。

### R20.1b `text` reader（待定，等实验结果）

用户在手机上用自带的识别文字功能（iPhone 实况文本、安卓 Google Lens）复制小票文字，粘贴进来。解析器是纯函数，按行处理：

- 行尾是金额（`6.75`、`$7.99`、`-$0.80`）的算一件商品，前面的部分是名字；名字前的 `*`、`(-%)` 这类标记去掉
- 只有数量、重量明细的行（含 `kg NET @`、`@ $x EACH`）跳过
- 负数行是单件折扣
- `DISCOUNT` 开头的行是整单折扣；`TOTAL`、`Total for` 开头的行是总额；`SUB TOTAL`、`GST`、`EFT`、`VISA`、`BALANCE`、`CHANGE` 这些行不算商品
- 日期：第一个 `DD/MM/YYYY` 或 `DD/MM/YY`；店名：第一个不是空行的行
- 付款：有 `EFT`、`VISA`、`MASTERCARD`、`DEBIT`、`CREDIT` → card，`*****` 或 `****` 后面的 4 位数是 `cardLast4`；有 `CASH` → cash；都没有 → unknown
- 解析不出总额或一件商品都没有 → 识别失败

**前提**：复制出来的文字里，商品名和价格在同一行。如果手机把名字和价格分成两列，这个 reader 做不了，先不做。2026-10-27 还没试，M6.7 里排在最后，试过再定。

### R20.2 整理和校验

reader 的原始结果（或用户在核对界面改过的）先整理：

- 金额字符串 → 整数分：去掉 `$` 和空格，`-$0.80`、`$-0.80`、`-0.80` 都是 -80。用 `money.ts` 的字符串口径，**不用 `parseFloat`**。格式不对就标在那一行上
- 日期：`DD/MM/YYYY` 和 `DD/MM/YY`（两位年份当 20YY），转成 `YYYY-MM-DD`。不能晚于今天（`Australia/Melbourne`）。读不出来就空着让用户填
- 店名、商品名、折扣名：去首尾空格，最长 100 字符，再按 R2.3 脱敏（8 位以上连续数字）
- `category` 不在分类列表里（LLM 编出来的、分类已归档）→ 当作 `null`，不报错
- 核对界面里手动填的商品走同样的整理和校验

能保存的条件（`checkReceipt`）：

- 总额 > 0（退货小票不做）
- 至少一件商品，每件金额 ≠ 0
- 整单折扣都 < 0
- **商品合计 + 整单折扣 = 总额**，差一分也不行。对不上时核对界面显示"差 $X"，保存按钮不能点，用户改到对上为止
- 日期有值

### R20.3 生成拆分

输入：整理好的小票、要挂上的交易（R20.4 匹配到的，或 R20.5 新建的）。交易的**主分类** = 当前主拆分的分类。

1. **每件商品的分类**：`category` 有值就用；`null` 跟主分类。负数商品（单件折扣）默认跟上一件商品的分类，第一行就是负数时跟主分类。核对界面上每一行都能改
2. **按分类合计**（小票方向，正数）
3. **整单折扣按比例分摊**：总折扣 D（取绝对值），商品合计 S，每组 g：先给每组 `floor(D × g / S)` 分，余下的几分给 g 最大的一组；一样大时主分类那组优先，再按商品顺序第一个出现的
4. **差额**：交易金额的绝对值 − 小票总额
   - = 0：不处理
   - \> 0（刷卡手续费、收银时取现等）：多出来的单独一组，分类未分类（system: uncategorized）。已经有未分类的一组就合进去
   - < 0：报错"小票合计比这笔交易多 $X，不支持"，不保存（可能是一部分用了别的方式付）
5. 分摊以后某组 ≤ 0：报错"X 合计不是正数，检查折扣跟在哪件商品后面"，不保存。= 0 的组不可能出现（每件 ≠ 0，负数组会报错），所以不用特别处理
6. **哪组当主拆分**：和主分类相同的那组；没有就取金额最大的一组（一样大取先出现的）
7. 写拆分（金额按交易符号，支出是负数）：
   - 主拆分：更新原来那行（id 不变）。分类没变 → `category_source` 不变；分类变了 → `manual`，归属人按 R5.1（`manual` 的不动）。备注保留
   - 其他组：新建拆分，`is_primary = false`。`category_source = manual`（用户在核对界面确认过），差额那组是 `system`；归属人按 R5 算（分类默认 > 卡号 > 账户），没有手动指定；`is_pre_tax` 按分类默认
   - 原来的非主拆分全部删掉（只有 R20.6 确认覆盖后才会有）
8. 合计永远等于交易金额（R15.1）

只有一组时（比如整张都是食品），结果就是交易不变，只多挂了一张小票。

### R20.4 匹配交易

从悬浮 + 按钮"拍小票"进来时，在本家庭找候选：

- `amount_cents` = −总额
- 交易日期 − 小票日期 ∈ [0, 3] 天（和 R8.2 一样，银行入账不早于消费）
- `transfer_status = none`（转账不能拆，R15.2；`suggested` 的也不要）
- 还没挂小票
- `pending`、`confirmed` 都算（包括手动录入的这笔消费）
- 卡号：小票有 `cardLast4`，并且本家庭 `card` 表里有这个尾号 → 只在这些卡所在的账户里找，交易的 `card_last4` 不为空时必须相同。`card` 表里没有这个尾号就不按卡号过滤

排序（给用户看的）：`card_last4` 和小票相同的在前；merchant 包含小票店名建议关键词（R3 清洗后取 R13 `suggestKeyword`，不区分大小写）的在前；再按日期差从小到大。

| 候选数 | 处理 |
| --- | --- |
| 0 | 按 R20.5 新建 |
| 1 | 默认选中，用户可以改成"新建"（R20.5） |
| ≥ 2 | 列出来让用户选，不默认选；也可以选"都不是，新建" |

从**交易详情**"上传小票"进来时，交易已经定了，不找候选、不检查日期，直接按 R20.3 处理（差额按第 4 步）。这个按钮只在支出、`transfer_status = none`、还没挂小票的交易上出现。

### R20.5 没有匹配时新建交易

小票通常当天拍，银行流水要过几天才导入，所以刷卡的小票不能直接记成现金：

| payment | 账户 |
| --- | --- |
| card，`card` 表里有这个尾号 | 默认选卡所在的账户（多个账户有同一个尾号时让用户选） |
| card，没有尾号或表里没有 | 用户选，默认 R17.2 的上次账户 |
| cash | 用户选，默认第一个没归档的现金账户 |
| unknown | 用户选，默认 R17.2 的上次账户 |

新交易：

- `status` 按账户走 R8.1：ANZ、CBA → `pending`，等导入 CSV 时按 R8.2 确认；现金、ANZ Plus → `confirmed`
- `source = receipt`，`date` = 小票日期，`amount_cents` = −总额
- `raw_description` = 店名（R20.2 整理后），`merchant` = R3 清洗结果
- `card_last4` 空（同 R17.1，银行流水确认时 R8.3 再填）
- 主分类：对 merchant 跑 R7 第 2、3 步（同 R17.2 猜分类），没命中就是未分类，`category_source` 按 R17.3
- 不跑 R6.1（同 R17.1）
- 然后按 R20.3 拆分

### R20.6 交易已经改过

要挂上的交易满足下面任何一条，算"已经改过"：

- 有多个拆分
- 主拆分的 `category_source = manual`

这时保存前弹窗："这笔已经手动改过（拆分 N 条 / 手动改过分类），用小票的结果覆盖吗？原来的拆分会删掉，主拆分的备注保留。" 确认后按 R20.3 重新拆；取消就不保存，回到核对界面。

### R20.7 和其他规则的关系

- **一张小票只能挂一笔交易，一笔交易只能挂一张小票**（`receipt.transaction_id` 唯一）
- **重复上传**：本家庭已有小票的店名（清洗后）、日期、总额都相同 → 核对界面提示"可能已经上传过"，不拦
- **R7.2 重新应用规则**：多个拆分的跳过，照旧。只有一组的小票交易不受影响
- **R8.2、R8.3**：R20.5 建的 pending 和手动录入的一样参加匹配；确认时拆分保留，`source` 保留 `receipt`，小票照样挂着
- **R12.1 撤销导入**：
  - 被删的交易挂了小票 → 小票脱开（`transaction_id` 变空，外键 `on delete set null`），变回"没挂上"的状态，可以重新匹配
  - 被确认的 pending 恢复成 pending → 小票照样挂着
  - 撤销前的弹窗里，"手动改过"的计数加一项"挂了小票 N 笔"
- **R17.5 编辑和删除**：`source = receipt` 的和 `source = manual` 的一样处理（还没被导入确认时能改、能删）。删除后小票脱开
- **R15**：保存以后拆分就是普通拆分，在详情页照常改。改拆分不改小票的 `parsed_json`
- **删除小票**：交易详情里能删掉小票，只删 `receipt` 那行，拆分不动
- **没挂上的小票**：F8 顶部提示"N 张小票没挂上交易"，点开列出来，每张能重新按 R20.4 匹配或 R20.5 新建
- **统计**（R10、R11、R14）按拆分算，不用改
