# M6.7：小票识别

> 目标：拍一张小票，商品按分类拆到对应的交易上；刷卡的小票先建 pending，等流水导入时自动确认。读小票的 reader 是注入的，用不用 AI、用哪家 LLM 改配置就能换；钱的计算全部是纯函数。
> 参考：`docs/prd.md` 第 4 节（小票识别、AI 功能）；`docs/business-rules.md` R5、R7、R8、R12.1、R15、R16.3、R17、**R20**；`docs/schema.md` receipt；`docs/tech-stack.md` 7、11；`fixtures/README.md` 小票用例；`docs/design/README.md`（14）
> 涉及页面或数据库的任务，先用 plan mode 说打算怎么做，我同意了再写。

## 通用要求

- 只加一张表 `receipt`（M6.7-1），不改别的表。不加新依赖：LLM 直接 `fetch`（tech-stack 11.2），图片压缩用 canvas
- 纯函数放 `src/lib/rules/receipt*.ts`，不 import 数据库和 Next.js；reader 接口和工厂放 `src/server/receipt-readers/`，LLM 调用放 `src/server/llm/`（tech-stack 11.3）；数据层放 `src/server/receipts.ts`；写入用 Server Actions + Zod
- 除了 reader 本身，任何代码都不能知道当前用的是哪个 reader（核对界面只看 `reader.input` 决定显示拍照还是粘贴）
- 金额字符串转分复用 `money.ts` 的口径，日期复用 `date.ts`，脱敏复用 `maskLongDigits`，清洗复用 `cleanMerchant`，关键词复用 `suggestKeyword`，分类猜测复用 `guessCategory`，归属人复用 R5 的函数，新建交易尽量复用 `buildManualTransaction`。不另写一套
- 分类下拉复用 F8 的 `category-picker`（可选范围按 R16.3，只要支出）
- 真实小票不进 git、不进测试、不进注释。测试只用 `fixtures/receipts/` 的假数据
- 图片不存、不打日志；`cardLast4` 不入库（R20.1）
- 全部带 `household_id`

## M6.7-3 按分类拆分（纯函数）

**做什么**

- `defaultItemCategories(items, mainCategoryId)`：`null` 跟主分类；负数商品跟上一件，第一行是负数跟主分类
- `allocateDiscount(groups, discountCents, mainCategoryId)`：R20.3 第 3 步，`floor` + 余数给最大的一组（一样大主分类优先，再按出现顺序）
- `planReceiptSplits(receipt, itemCategories, tx, ctx)`：R20.3 全部步骤，返回主拆分的更新、要新建的拆分、要删的拆分，或者报错（差额 < 0、某组 ≤ 0）。归属人用 R5 的函数
- 测试名带规则编号，如 `it('R20.3: whole-receipt discount remainder goes to the largest group')`

**完成标准**

- R-A：#19 拆成 -31.40 / -15.00 / -12.00，归属人 Home（category）/ Home（category）/ Male（card 1111），主拆分 `category_source` 还是 `rule`
- R-B：-19.39 / -9.70 / -3.24，合计 -32.33
- R-C：-59.28 多一组 -0.88 未分类（`system`）；-50.00 报错，信息带 $8.40
- 只有一组时：主拆分不变，没有新建
- 主分类那组不存在时（交易原来是未分类）：最大的一组当主拆分，`category_source = manual`，归属人按 R5.1；主拆分 `member_source = manual` 时归属人不动
- 单件折扣比上一件还大、让那组 ≤ 0：报错
- 任何结果拆分合计都等于交易金额
