# 任务清单和开发流程

> 每个里程碑一份文件，**做到哪个才拆哪个**。现在拆好的是 M0、M1、M2。
> 一个任务 = 一次 Claude Code 会话 + 一个 commit。

---

## 进度在哪里看

| 地方               | 记什么           | 什么时候更新                        |
| ------------------ | ---------------- | ----------------------------------- |
| `docs/tasks/mN.md` | 每个任务的勾     | 每做完一个任务，和代码一起 commit   |
| `docs/roadmap.md`  | 里程碑验收清单   | 里程碑做完时                        |
| git log            | 每个任务改了什么 | 自动，commit message 以任务编号开头 |

不用 GitHub Projects、Jira 之类的工具。

**仓库里的文档是正本。** claude.ai Project 里的副本只用来聊规划。改了规则要同步，别让两份越走越远。

## 标记

| 标记          | 含义                                                      |
| ------------- | --------------------------------------------------------- |
| `[ ]` / `[x]` | 未完成 / 完成                                             |
| 🧑            | 需要我自己动手（注册服务、填密钥、看真实数据），不交给 AI |
| 🔒            | 前置任务没完成不能开始                                    |

## 每个任务的循环

### 1. 开始

- 从 main 拉分支，名字带任务编号：`git checkout -b m2-5-merchant`
- Claude Code 开新会话（`/clear`），从干净的上下文开始

### 2. 交代任务

粘贴下面的提示词，改任务编号：

```
做任务 M2-5。
先读 CLAUDE.md、docs/tasks/m2.md 里 M2-5 的说明，以及它列出的文档章节。
先写测试，跑一遍确认失败，再写实现。
只做这一个任务，做完停下来，告诉我改了哪些文件、怎么验证。
```

涉及页面或数据库的任务，先让它用 plan mode 说打算怎么做，我同意了再写。

### 3. 先审测试，再审实现

**这一步最值得花时间。** 测试里的期望值就是规则本身，测试错了，实现再对也没用。

- 对照 `business-rules.md` 和 `fixtures/README.md`，看期望值是不是照抄的
- 确认测试先跑失败，再写实现
- 实现只需要看有没有违反 `CLAUDE.md` 的硬规则

### 4. 自己验证

- `pnpm test`、`pnpm lint` 通过
- 对照任务的"完成标准"逐条检查
- 有界面的任务：`pnpm dev` 在电脑浏览器里点一遍；再把窗口调到 375px 宽，确认没有横向滚动、没坏

### 5. 收尾

- 在 `tasks/mN.md` 里打勾，和代码一起 commit：`M2-5: clean merchant names (R3)`
- push，开 PR。Vercel 会给 PR 一个预览地址，快速录入相关的任务用手机打开看
- 合并到 main，自动部署到线上

## 遇到这些情况

| 情况                     | 做法                                                 |
| ------------------------ | ---------------------------------------------------- |
| 发现规则没写到的边界情况 | 停下，先改 `business-rules.md` 和 fixtures，再改代码 |
| AI 改了两三轮还没好      | 别继续追问。`/clear`，把任务拆小重新来               |
| AI 想加新依赖或改表结构  | 按 `CLAUDE.md` 它应该先问。确认了再继续              |
| 任务做到一半发现太大     | 拆成 M2-5a、M2-5b，在任务文件里改掉                  |
| 测试和文档对不上         | 以文档为准修实现；如果是文档错了，先改文档           |
| 线上出问题               | 回滚到上一个部署（Vercel 后台一键），再查原因        |

## 每个里程碑结束

1. 跑一遍 `roadmap.md` 里这个里程碑的验收清单
2. 电脑上点一遍线上版本，手机上打开确认不坏
3. 回顾：做的过程中改过哪些规则？有没有影响后面的里程碑？
4. 拆下一个里程碑的任务（回 Project 聊，或让 Claude Code 照 `m2.md` 的格式拆，我再审）
